01 / 定位

它是什么：一个「官方调优版」而不是「替代品」

DeepInfer 是 DeepSeek 内部的推理引擎，负责把 V4.1-Flash 跑在其自有集群上， 属于「模型之外、算子之上」的那层调度与执行系统。

官方定位 
DeepInfer is the high-performance inference framework that powers
DeepSeek's large-scale production services. This open-source release
provides offline inference with the core features needed for serving at scale.

—— github.com/deepseek-ai/DeepInfer

把它拆成三句话说清楚：

血统

站在 vLLM 肩上

README 致谢章节明确写着「originally built primarily on vLLM」。所以它是 vLLM 的深度定制分支式实现，而非另起炉灶。

差异化

只为自家架构调优

FlashMLA、DeepGEMM、DeepEP、TileKernels、DeepSelect 这些自家算子被直接焊进引擎，围绕 MLA + MoE + SWA 做端到端优化。

现状

开源的是「离线版」

官方明确列出未包含：KV cache 系统、VE/Prefill/Decode 分离部署、跨 DP 副本的负载均衡。在线服务能力仍需自建或等更新。

一句话理解：vLLM 是「什么模型都能跑」的通用底座；DeepInfer 是「只把 DeepSeek 模型跑到极致」的官方参考实现。两者不是同一维度的竞品，更像是「通用解」与「特化解」的关系。

02 / 背景

DeepSeek 为什么要把「中间层」也开源

时间线：仓库于 2026 年 10 月 16 日上线，10 月 20 日 DeepSeek 正式宣布全面开源，同步放出 deepseek-recipe。

DeepSeek 此前已经陆续开源了模型权重、TileLang 编译工具，以及 FlashMLA / DeepGEMM / DeepEP 等算子库。 但这些都是「零件」——真正决定一张卡一天能产出多少 token、烧多少电的，是中间那层推理框架。

官方公告里的逻辑很直白：模型能力由模型本身决定，但能否以合理成本提供超大规模服务，取决于推理框架； 而框架效率直接决定了算力成本与电力消耗。开源这套内部部署经验，是希望开发者与企业能优化吞吐与延迟、降低单位 token 成本。

这次开源的两个仓库

主仓库

deepseek-ai/DeepInfer

推理引擎本体：算子集成、并行策略、投机解码、调度、结构化输出。Apache 2.0。

配套组件

deepseek-ai/deepseek-recipe

Rust 编写 + Python 绑定：把 Messages / Chat Completions / Responses 统一转成内部 Conversation，渲染成 prompt 并编码成 token，使自托管行为与官方 API 对齐。

容易被忽略的点：很多团队自建 DeepSeek 服务时，模型跑得动，但输出和官方 API「味道不一样」——根因往往不是模型，而是 prompt 渲染与 token 编解码的细节差异。deepseek-recipe 解决的正是这个「最后一公里」的对齐问题，而且可以脱离 DeepInfer 单独使用。

03 / 架构

五层结构：从 API 到算子全栈打通

DeepInfer 的价值在于把此前分散开源的一堆「零件」装成了一台整机。自下而上看，大致是这五层：

接入 / 编解码deepseek-recipe
Messages Chat Completions Responses Prompt 渲染 Token 编解码 多模态预处理
引擎 / 运行时LLM · Scheduler
异步批调度 采样器 结构化输出 确定性推理 KV 管理
并行 / 通信DP · CP · EP
Attention DP 均衡 CP MoE EP EPLB 专家负载均衡 DSpark 投机解码
算子层自研 kernel
FlashMLA DeepGEMM DeepEP TileKernels DeepSelect TileLang 自定义算子
硬件层双平台
NVIDIA SM100 (Blackwell) Huawei Ascend 950

这个分层解释了一个常见疑问：为什么 DeepInfer 只支持 V4.1-Flash、只支持 SM100？ 因为整条栈都是为特定模型形态和特定指令集调过的——通用性被主动牺牲，换来的是端到端效率。

04 / 核心

相对 vLLM，它到底改了什么

逐条对应官方 README 的 Feature 列表，并标注「通用框架的常规做法」与「DeepInfer 的差异」。 需要强调：这些是垂直场景下的深度优化，不是 vLLM 的缺陷。

1

FlashMLA：把 MLA 的注意力内核换成专用的

Multi-head Latent Attention · 显存带宽是第一瓶颈

V3/V4 系列的 MLA 会把 KV 压缩成低秩潜向量，注意力的性能瓶颈从「算力」转向「KV 读取带宽」。通用框架要走 FlashAttention / FlashInfer 这类统一 backend，需要兼顾各种 head_dim 与布局，难以把 MLA 的压缩布局吃到极致。

通用做法
统一 attention backend + 针对 MLA 的特殊分支，兼容性优先。
DeepInfer
直接集成自家 FlashMLA，按 MLA 的压缩 KV 布局写内核，把「解压 + 注意力」融合在一趟里完成。
收益
长上下文解码时的 KV 带宽压力下降，单卡可承载更长序列 / 更高并发。
FlashMLA decode 阶段主力 长上下文
2

MoE EP + EPLB：让热点专家不再排队

Expert Parallelism + Expert Parallel Load Balancer

MoE 模型每个 token 只激活少数专家，但路由是动态的：某些专家在特定 batch 里会被挤爆，其余专家却闲着。这是 MoE 服务里最典型的「木桶效应」——整批 token 的延迟由最慢的那个专家决定。

EP 把不同专家分到不同卡，token 靠 all-to-all 送到「持有该专家的卡」。关键在于：送哪儿不是写死的，而是一张运行时可改写的映射表（逻辑专家 → 物理副本 → 卡）。EPLB 不碰路由逻辑，只周期性地改写这张表。

所以「动态」不是给某个专家临时加算力，而是一个三步闭环：

  • 统计：每个 step 累计本地各物理槽位收到的 token 数，写入滑动窗口（默认 100 步，示例为省显存设 3）。
  • 重算：每 N 步（示例 30）把窗口按副本映射聚合、在 EP 组内 all_reduce 成全局负载，再贪心解两件事——给哪些热门专家加冗余副本、所有副本怎么铺到各卡，使「最忙那张卡」的历史峰值最小。
  • 搬运：按新布局 shuffle 专家权重（机内走 symmetric memory / IPC 直拷，只镜像一层、逐层复用），再原子切换映射表，下一步生效。

能成立的前提有三条：专家权重是独立可寻址的参数块，搬一个专家 = 拷贝一段显存 + 改索引；路由分布是慢变的，用历史窗口预测下一个窗口足够准；重排频率低，搬运可安排在 prefill 之后并逐层重叠。

通用做法
TP 或静态 EP，专家到卡的映射在启动时确定，靠容量因子（capacity factor）丢弃/填充来兜底。
DeepInfer
保留逻辑专家全集 + 冗余物理槽（extra 默认下限 32，按 EP 规模向上取整到可整除），按窗口负载重排副本与摆放，并在线搬运权重。
收益
最忙 rank 的峰值负载下降——被削平的是「卡与卡之间」的木桶板。
--ep / --dp / --cp EPLB（默认开） EXPERT_COUNT_WINDOW_SIZE EXPERT_REARRANGEMENT_STEP_INTERVAL

它均衡的是「放置」，不是「路由」：单个 batch 内某专家仍可能被挤爆（那是容量因子 / 路由偏置要处理的事）；EPLB 解决的是「长期热点导致某几张卡持续拖后腿」。

3

DSpark + 置信度调度验证：投机解码不再「一把梭」

Speculative decoding with confidence-scheduled verification

投机解码（草稿 token + 并行验证）的收益高度依赖「草稿命中率」。固定窗口的验证策略在草稿质量差时会白白浪费算力，在草稿质量好时又没吃满加速比。

通用做法
n-gram / EAGLE / MTP 等草稿方案，验证策略多为固定长度或简单阈值。
DeepInfer
DSpark 生成草稿，再用「置信度估计」动态决定验证时机与长度，低置信度就少验、高置信度就多验。
收益
decode 阶段的有效吞吐提升，且避免无效验证带来的算力浪费。
bash 
# 开启变长 MTP（投机解码），草稿长度上限 5
DEEPINFER_ENABLE_MTP_VARLEN=1 DEEPINFER_USE_NEXTN_DECODE=5 \
  python examples/offline_inference.py
4

SWA Bounded Replay：decode 阶段只重放「有界后缀」

Sliding Window Attention · 少算一大截 prefill

滑动窗口注意力意味着模型真正「看得到」的只有最近一段上下文。DeepInfer 在 decoder 阶段复用时，只重放一个有界后缀，而不是把历史全量重算。

通用做法
依赖 prefix caching / chunked prefill 复用 KV，但不会针对 SWA 窗口做「最小必要重放」的裁剪。
DeepInfer
只重放覆盖 SWA 窗口 + 最大回溯长度的后缀，V4.1 默认保留 140 个 token。
收益
decode 路径上的 prefill 计算量显著减少，长对话/多轮场景收益更明显。
bash 
DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=compact \
DEEPINFER_YOCO_PREFILL_KEEP_TOKENS=140 \
  python examples/offline_inference.py
5

异步调度：CPU 组批与 GPU 计算重叠

Zero-overhead batch scheduler · 默认开启

小 batch、短序列的 decode 场景里，CPU 侧组 batch 的开销常常追不上 GPU 的算力，导致 GPU 空转。DeepInfer 把批调度与设备执行做成异步流水，默认启用，无需配置。

通用做法
同步式 step 循环，调度与执行串行（vLLM 也在持续优化这一点，如异步输出处理）。
DeepInfer
零开销批调度器，CPU 侧准备工作与上一次前向计算重叠。
收益
低延迟场景下 GPU 利用率更高，小 batch 的 CPU 瓶颈被掩盖。
默认开启 DEEPINFER_LOGGING_INTERVAL_STEP 可观测
6

Batch-invariant 与确定性采样：同输入必得同输出

对 RL 训练、评测、回归测试是刚需

常规推理里，同一 prompt 的 logits 会随 batch 组成不同而产生数值差异（不同 kernel 的归约顺序、不同的 GEMM 分块），导致「温度=0 也不完全可复现」。这对做 RL rollout、A/B 评测、线上回归的团队是实打实的痛点。

通用做法
通常只保证「采样随机种子可设」，不保证跨 batch 组成的数值一致性。
DeepInfer
DEEPINFER_BATCH_INVARIANT=1 保证不同 batch 组合下模型结果一致；再关闭变长 MTP 并传入固定 seq_seed，即得确定性输出（仅 NVIDIA 平台）。
收益
可复现的实验与线上回归；RL 训练与推理对齐更可靠。
bash 
DEEPINFER_BATCH_INVARIANT=1 DEEPINFER_ENABLE_MTP_VARLEN=0 \
  python examples/offline_inference.py
7

结构化输出：regex / JSON Schema / EBNF 三件套

约束解码作为引擎一等能力

通过 SamplingParams(so_args=...) 直接施加输出约束，支持正则、JSON Schema 与 EBNF 文法——比只支持 JSON 的约束更通用（例如生成 DSL、SQL 片段、专用报文格式）。

通用做法
vLLM 有 guided decoding（outlines / xgrammar），SGLang 有 compressed FSM，能力强弱取决于后端编译器。
DeepInfer
内置为采样器能力，三种 schema_type 统一入口，示例代码可直接对照。
收益
Agent / 工具调用 / 数据抽取场景下，省掉外层重试与解析容错逻辑。
python 
from deepinfer.sampling_params import SamplingParams

so_args = {
    "schema_type": "ebnf",   # "regex" | "json" | "ebnf"
    "schema": 'root ::= "answer=" ("yes" | "no") ";level=" [1-3]',
}

outs = llm.generate(
    prompts=["请判断这条评论是否推荐该产品。"],
    sampling_params=SamplingParams(temperature=0, max_tokens=128, so_args=so_args),
    use_tqdm=False,
)
8

昇腾 950 原生支持：vLLM 至今没有的能力

国产算力落地的现实选项

vLLM / SGLang 的主战场是 NVIDIA（vLLM 另有 ROCm、TPU 等插件生态），对昇腾没有官方原生支持。DeepInfer 通过 DEEPINFER_ACCELERATOR=ascend 一键切换构建目标，走 CANN 9.2 栈。

通用做法
需要第三方适配层或厂商自研框架，版本滞后、算子覆盖不全。
DeepInfer
同一套代码双后端，构建时选择 accelerator，官方承诺后续持续更新。
收益
有昇腾集群的团队，第一次能拿到「官方同款」而非魔改版。

别误读这 8 条：DeepInfer 没有发明新的并行范式，也没有解决在线服务的全部问题。它的稀缺性在于「DeepSeek 自己在用」——这意味着这些取舍（只支持一种模型、一代硬件）是被真实生产流量验证过的，而不是论文里的最优解。

06 / 前置条件

硬件门槛与能力边界：先确认你跑得起来

支持

两代平台，别无分号

NVIDIA SM100（Blackwell，如 B200 一档）配 CUDA 13；华为昇腾 950 配 CANN 9.2。系统要求 Linux、GCC ≥ 13、Python 3.12。

不支持

消费级与上一代数据中心卡

A100 / H100 / RTX 4090 等均不在支持列表。想在 4090 上跑 DeepInfer 目前没有路径，请继续用 vLLM + 量化。

已具备

离线推理的完整核心

并行策略、投机解码、SWA 回放、异步调度、确定性推理、结构化输出——README 列出的能力都可直接用。

尚缺

在线服务三件套

KV cache 系统、VE/Prefill/Decode 分离部署（引擎侧大部分已实现）、跨 DP 副本的 prefill/decode 负载均衡。

一个流传较广的笔误：部分中文解读把支持硬件写成「SM100（Blackwell，如 H200/B200）」。H200 属于 Hopper（SM90），并非 SM100。请以官方 README 的「NVIDIA SM100 GPUs」为准。

07 / 上手

快速上手：从源码到第一条输出

官方只提供源码构建路径，没有 pip install。以下命令均来自仓库 README 与 build.sh。

准备一个干净的 Python 3.12 环境

官方特别提示：构建前请创建一个空的 Python 3.12 环境，避免与已有 CUDA / torch 版本冲突。

bash 
git clone https://github.com/deepseek-ai/DeepInfer.git
cd DeepInfer

python3.12 -m venv .venv
source .venv/bin/activate
python -V   # 必须是 3.12.x

选择加速卡后端并构建

build.sh 会做四件事：装 requirements、把 NCCL 打到 2.32.3（仅 NVIDIA）、编译 vendored 依赖、编译并安装 DeepInfer。这个过程较慢，建议预留时间。

bash 
export DEEPINFER_ACCELERATOR=nvidia
./build.sh

# 构建完成后，这个变量仍需保留在运行环境中
bash 
export DEEPINFER_ACCELERATOR=ascend
./build.sh

# 依赖 CANN 9.2，构建前请确认驱动与工具链就绪

跑通官方离线示例

默认加载 deepseek-ai/DeepSeek-V4.1-Flash-1017，首次运行会自动下载到 HuggingFace 缓存。想用本地权重就设 DEEPINFER_HF_MODEL_DIR。

bash 
# 默认：自动下载 V4.1-Flash-1017
python examples/offline_inference.py

# 或使用本地权重目录
DEEPINFER_HF_MODEL_DIR=/path/to/DeepSeek-V4.1-Flash-1017 \
  python examples/offline_inference.py

示例脚本的默认并行配置为 --ep 8、--cp 1，并按 dp = ep / cp 推导 DP 规模；max_num_batched_tokens=32768、max_model_len=32768、gpu_memory_utilization=0.85。

按机器规模调整参数

可用参数一览（来自 examples/offline_inference.py 的 argparse 定义）：

bash 
python examples/offline_inference.py \
  --model_name deepseek-ai/DeepSeek-V4.1-Flash-1017 \
  --ep 8 \
  --cp 1 \
  --dp 8 \
  --sampler_force_topk 4096 \
  --long_context \
  --check_structured_output
参数含义默认
--ep专家并行度（MoE EP）8
--cp上下文并行度（均衡 CP）1
--dp数据并行度，不填时按 ep / cp 推导ep // cp
--disable_eplb关闭专家负载均衡（排查异常时可关）不关闭
--sampler_force_topk采样器的强制 top-k 规模4096
--long_context每条样本 16389 输入 + 4096 输出关闭
--check_structured_output生成后用同一模型自检结构化输出关闭

脚本内还有一条断言：world_size = dp × cp 必须能被 ep 整除，否则直接报错。排机器拓扑时先算清这一点。

在代码里直接调用 LLM

接口风格与 vLLM 高度相似（LLM + SamplingParams），迁移成本主要在于环境与算子，而非代码写法。下面这段是示意：底层引擎由 create_llm() 组装（见 examples/_config.py），部分关键字参数名请以 deepinfer/entrypoints/llm.py 为准。

python 
import os
os.environ["DEEPINFER_ACCELERATOR"] = "nvidia"

from deepinfer.entrypoints.llm import LLM
from deepinfer.sampling_params import SamplingParams

llm = LLM(
    model="deepseek-ai/DeepSeek-V4.1-Flash-1017",
    max_model_len=32768,
    max_num_batched_tokens=32768,
    max_num_seqs=4,
    gpu_memory_utilization=0.85,
)

outs = llm.generate(
    prompts=["用三句话解释 MoE 的专家并行。"],
    sampling_params=SamplingParams(temperature=0.6, max_tokens=256),
    use_tqdm=False,
)

# 每个 out 是可迭代的 token 序列，末位为结束标记
for out in outs:
    text = llm.get_tokenizer().decode(
        [t.token_id for t in out[:-1]],
        skip_special_tokens=False,
        clean_up_tokenization_spaces=False,
    )
    print(text)

没有 HTTP Server：这个版本主打离线推理，README 的 Getting Started 只有 offline_inference.py 一条路径。要对外提供 OpenAI 兼容接口，需要自己在 LLM 之上包一层服务（或等官方补齐在线能力）。

结构化输出：三种约束形态

官方示例 examples/_structured_output.py 给了三种 schema_type，并断言每种都能以 EOS 正常收尾：

python 
import json

cases = [
    # 正则：生成形如 AB-123 的编号
    {"schema_type": "regex", "schema": r"[A-Z]{2}-[0-9]{3}"},

    # JSON Schema：字段与枚举都被约束
    {"schema_type": "json", "schema": json.dumps({
        "type": "object",
        "properties": {
            "color": {"type": "string", "enum": ["red", "green", "blue"]},
            "count": {"type": "integer", "enum": [1, 2, 3]},
        },
        "required": ["color", "count"],
        "additionalProperties": False,
    })},

    # EBNF：适合自定义文法 / DSL
    {"schema_type": "ebnf",
     "schema": 'root ::= "answer=" ("yes" | "no") ";level=" [1-3]'},
]

outs = llm.generate(
    prompts=[...],
    sampling_params=[SamplingParams(temperature=0, max_tokens=128, so_args=c)
                     for c in cases],
    use_tqdm=False,
)

deepseek-recipe：让输出「长得像官方 API」

与 DeepInfer 同步开源，可独立接入 vLLM / SGLang / TensorRT-LLM 等任意后端。Python 3.10+ 即可安装使用。

bash 
python3 -m pip install deepseek-recipe
python 
from deepseek_recipe import (
    ChatCompletionRequest, ConversionOptions, DeepseekV41Encoding,
)

request = ChatCompletionRequest({
    "model": "DeepSeek-V4.1-Flash",
    "messages": [{"role": "user", "content": "Hello"}],
})

converted = request.convert(ConversionOptions())
rendered = DeepseekV41Encoding().render_conversation(converted.conversation)
print(rendered.prompt)

它负责的是「请求格式 → 内部 Conversation → prompt / token」这一段，并内置了几个容易踩坑的默认值：

  • resolve_max_tokens 在未指定时自动兜底：普通模式 8192，思考模式 65536，思考模式 max effort 131072。
  • 支持 Messages / Chat Completions / Responses 三种协议互转，含流式响应与 prefix 续写。
  • 图像以 base64 或外链传入，V4.1 会做预处理；V4 不支持图像，会被替换为 [Unsupported Image]。
  • 安全提示：ReqwestImageFetcher 默认可访问任意地址，面向不可信请求时务必配置 DestinationFilter（防 SSRF）。

实践建议：即使短期内不迁移到 DeepInfer，也值得单独接入 deepseek-recipe。它带来的收益（与官方 API 行为一致）是立刻可验证的，而风险仅限于编解码层，不触碰你的推理引擎。

10 / 答疑

常见问题

DeepInfer 是 vLLM 的竞品还是分支？

官方措辞是「originally built primarily on vLLM」，并致谢 SGLang 与 TensorRT-LLM。它不是 vLLM 的 fork 分支（仓库独立、代码组织不同），但设计上大量继承了 vLLM 的引擎骨架。准确说法是：以 vLLM 为基础的深度定制实现。

和 vLLM 跑同一个模型，到底快多少？

官方没有发布对比数字，只有自家 4+64 卡配置下的 Pareto 曲线。任何「快 X 倍」的说法都缺少官方出处。如需决策，请用 examples/sweep/run_sweep.sh 在相同硬件、相同模型、相同并发下自测。理论上 FlashMLA + SWA Replay + DSpark 会给 decode 侧带来可感收益，但幅度强依赖上下文长度与 batch 形态。

RTX 4090 / A100 / H100 能跑吗？

不能。README 明确只支持 NVIDIA SM100 与昇腾 950。注意 H100 / H200 属于 Hopper（SM90），不在列表内；部分中文文章把 H200 写成 SM100 是笔误。

能直接当在线服务上线吗？

不建议。开源版是离线推理版本，官方列出三项缺失：KV cache 系统、VE/Prefill/Decode 分离部署（引擎侧大部分已实现）、跨 DP 副本的 prefill/decode 负载均衡。另外也没有现成的 HTTP Server 与 OpenAI 兼容层。

为什么只支持 V4.1-Flash？其他模型呢？

因为整条栈（算子、EPLB、SWA 回放参数如 keep_tokens=140）都是针对该模型的层数、专家数、窗口大小调的。官方表示新模型的推理代码与优化会持续更新到仓库，但未给出时间表。

deepseek-recipe 必须配合 DeepInfer 用吗？

不需要，它是独立库，可接任意后端（vLLM / SGLang / TensorRT-LLM）。它只负责协议转换、prompt 渲染与 token 编解码，模型推理、工具执行、HTTP 传输仍需调用方自己提供。

Apache 2.0 可以商用吗？有什么坑？

可以商用、可修改、可闭源分发，只需保留版权与许可声明。真正的「坑」不在许可证，而在工程完备度：在线服务组件缺失、只支持一代硬件、需要源码构建。建议先做 PoC 再谈生产。

构建失败最常见的原因？

按官方前置条件逐项核对：Linux、GCC ≥ 13、Python 严格 3.12、NVIDIA 需 CUDA 13（Ascend 需 CANN 9.2），且务必在空环境中构建——build.sh 会强制重装 NCCL 2.32.3 并编译 vendored 依赖，与已有 torch 环境冲突时现象往往很隐蔽。
